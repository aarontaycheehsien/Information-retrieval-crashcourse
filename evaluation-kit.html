Local retrieval evaluation kit

Portable spreadsheets, with Excel as the primary target. No macros, accounts or external data connections. Download and save your own copy; entries stay in that file. Google Sheets import is not a tested workflow for this release.

Start with one comparison

Open the completed example first, then use the template for a search you know well enough to judge. It contains five prompts covering four deliberate probes: an exact identifier, evidence found only in full text, vocabulary mismatch, and two queries with opposite meanings. Replace the prompts with local needs and criteria; the template supplies no product results or relevance labels.

A useful institutional set can grow to thirty to fifty queries. Constructing needs and judging hundreds of results takes time. An afternoon may be enough to rerun an established set; it is not a promise for building one.

Where to work
WorksheetWhat it holds

QueriesWrite the need and relevance criteria, record both queries and filters, confirm capture depth and counts, then explain the difference.
RecordsKeep one row per query–record pair, with a single relevance judgement, seed status and a rank for each run that returned it. The columns after Rank B calculate validation and counts.
RunsRecord the product, mode, date, available model/index information, change being tested and locations of saved exports. Write “unknown” for unavailable details.

Pale yellow cells are inputs; grey cells calculate. Use unique text IDs without surrounding spaces. IDs are compared without case sensitivity: A and a identify the same record. Use one canonical DOI, PMID or local ID consistently across both runs.

Six steps to a repeatable comparison

  1. Define relevance before looking at the scores. In Queries, write a specific need and criteria another person could apply. Enter both exact queries; record filters as “None” where appropriate. Select known relevant seeds before inspecting the comparison. In Records, mark them Seed = Yes, including seeds that neither run found. A seed need not be in either captured list.
  2. Choose the cutoff and record the conditions. Use 10 or 20 in Comparison B4, shared by both runs and every query. Complete Runs and retain each query’s transformed input, or mark it unknown. A comparison can test a query intervention, an update or a different product; record which conditions changed.
  3. Capture each list through that depth. Save the original output. Record the requested capture depth in Queries, the number of distinct records retained and whether capture is complete. A complete empty list has count 0 and Complete = Yes; an unperformed run stays incomplete. If the product returns only three results when ten were requested, depth is still 10 and count is 3.
  4. Pool the records, preserving ranks. Match identifiers manually across the two lists. For each query–record pair, enter its original position in Rank A and/or Rank B. Leave a rank blank when absent; do not use zero. If a record repeats within a run, retain its first occurrence and leave the resulting gap in the ranks. Do not pull a record from below the cutoff into that gap. Record the duplicate in Evidence or notes; the captured count is the distinct count after this step.
  5. Judge every pooled record inside the cutoff once. Use Relevant or Not relevant against the written criteria and record the basis where needed. Unjudged and blank both mean work remains. Hide the Seed and Rank A/B columns, and the calculated columns to their right, while judging; avoid opening Comparison. This reduces visible cues but is not a fully blinded assessment. Discuss disagreements and record the agreed judgement.
  6. Inspect individual queries. Fix any status message, then compare A and B. Negative differences are highlighted, without claiming statistical significance. Use Queries to record an explanation, alternatives and the next check. The workbook does not infer a mechanism or recommend a vendor.

The four probe types test different possibilities. Failure to retrieve a full-text-only phrase is evidence to investigate the indexed unit, not proof of its architecture. Judge the two opposite-meaning queries separately. Consult Chapter 13’s diagnosis frame before attributing a change to a mechanism.

What the scores count

Precision@k = relevant distinct records within k ÷ k. The denominator stays fixed, even for a short list or duplicate positions. Two relevant records from a complete three-result run at depth ten give 2/10 = 0.20. The separate “Records A/B at k” columns show how many distinct records were actually captured inside the cutoff.

Known-seed recovery@k = listed seeds found within k ÷ all listed seeds for that query. Include missed seeds in Records with both ranks blank. The numerator and denominator are shown alongside the rate. Without a seed set the workbook says “No seeds specified”; precision can still be calculated. Seed recovery is not an estimate of complete recall.

The precision comparison stays blank until every pooled record within the cutoff has been judged. Seed recovery can be available before those judgements are complete, because its denominator was fixed in advance. A seed marked Not relevant is an inconsistency to resolve.

Incomplete captures, missing criteria or exact queries, mismatched counts, duplicate IDs or ranks, and invalid input withhold affected scores. Blank cells are not silently turned into successful zero-result runs. Records with missing or unknown query IDs must be assigned before any query can be reported.

Changing k from 10 to 20 requires captures through twenty for both runs. Increasing the setting alone will show “Extend capture to the selected cutoff”. Capture depth records the depth requested, not the largest rank returned. Additional results beyond the active cutoff do not affect scores until the cutoff reaches them.

Add records, extend the set and rerun it

The template has room for fifty queries and starts with one hundred Records rows. In Excel, add rows inside the Records table or press Tab in its last cell to extend it; copy the calculated columns I–Q from the preceding row if your spreadsheet application does not fill them automatically. Check that Row status and counts respond before continuing. Pasting underneath an unextended table does not add records to the calculation.

To exceed fifty queries, extend the Queries table and copy its T–U formulas into the new rows. Extend Comparison by the same number of rows and copy all A–Q formulas down. Keep the two tables in corresponding row order when extending them. Use Comparison’s filters to inspect declines; sort Queries or Records as whole tables, never isolated input columns. Record matching uses query IDs, not row order.

For a new comparison, save a new workbook copy. Keep the same needs, criteria, seed set and cutoff. Replace ranks, captured counts and run metadata with the new observations and reconfirm completeness. Reuse judgements only where the record identity and criteria remain the same; judge newly retrieved records before interpreting the comparison. Changing the need or criteria starts a new evaluation baseline.
