# Plan: Markdown as the textbook's authoring source

Date: 2026-11-26. Reviewed edition: version 1.2.1, commit `0e3d4f8`.

## Recommendation

Make Markdown the authoring source and keep `search-textbook.html` as a
committed build output that stays equivalent to the current published page.
The conversion should not also be a redesign. Every generator and checker in
`tools/` reads the HTML by class, id and marker, so an equivalent output means
none of them needs rewriting at the start.

## Findings that shape the plan

- `search-textbook.html` is 1.37 MB, about 104,000 words in chapter sections,
  with 1,012 ids, 242 `<details>`, 49 tables, 74 figures, 5 inline SVGs,
  56 footnote references, 26 MathJax expressions and about 1,030 lines of
  inline CSS.
- About 49% of chapter words sit in plain `p`, `ul`, `blockquote`, `h3`
  markup that converts cleanly. About 21% is generated by
  `build-product-claims.py` (claim entries, claim links, coverage) and should
  never be authored in Markdown. The remaining 30% is custom components:
  figures, worked cards, stage maps, asides, self-checks and chapter headers.
- At least 17 tools read the HTML: `maintain.py`, `renumber_footnotes.py`,
  the product-claims, glossary, digest and questionnaire builders, and their
  tests. `data/product-claims.json` validates exact normalised excerpts
  against anchors.
- There is no CI. GitHub Pages serves committed files, so the built HTML must
  stay committed.
- The WYSIWYG annotation editor writes to the HTML directly. After the
  switch it would be editing a build output.
- Tables are simple: no `colspan`/`rowspan`, no block content in cells.
- Pandoc 3.1.3 is available. Fenced divs, header attributes, native footnotes,
  raw HTML passthrough and Lua filters cover most custom markup
  ([Pandoc User's Guide](https://pandoc.org/MANUAL.html)).

## Phases and exit criteria

0. **Agree the goal.** Ease of editing, cleaner diffs, AI-assisted editing, or
   other formats (EPUB/PDF). This decides whether "output equivalent" is a hard
   rule or only the starting point. Exit: a written goal and a decision on the
   annotation editor.
1. **Baseline and equivalence check.** `tools/html-equivalence.py` normalises
   the page to a canonical DOM (text, ids, classes, attributes, element order)
   and compares two builds. Snapshot the current book as the reference. Exit:
   the current file compared with itself passes; a deliberate edit fails.
2. **Mapping spec.** Element to Markdown construct: headings as
   `### Title {#id}` (heading anchor added by the build); asides, worked cards
   and stage maps as fenced divs; self-checks as a `self-check` div
   convention; footnotes as `[^n]` with a Lua filter emitting the book's
   current markup (making `renumber_footnotes.py` redundant); figures as a
   fenced div with slug and title; inline SVG and complex worked figures as
   raw HTML includes under `book/figures/`; maths passed through untouched;
   Pandoc's `smart` extension off so quotes, dashes and the 60 `&nbsp;` survive.
   Exit: every surveyed class has a mapping or is marked raw HTML.
3. **Pilot one chapter.** Convert Chapter 2 and iterate until its section is
   DOM-equivalent. Exit: equivalent and readable. If the Markdown is mostly raw
   HTML, stop and reconsider.
4. **Split and convert.** `book/NN-slug.md` for front matter, 15 chapters,
   7 appendices and back matter, plus `book/template.html` for head, CSS and
   scripts. Generated regions (claims register and links, glossary nav and
   lookup, tables of contents, figure and table indexes) are not authored.
   Exit: full build matches the baseline.
5. **Build pipeline.** `tools/build-book.py`: Pandoc with Lua filters, then
   assembly, `maintain.py`, product claims, glossary hub, digest,
   questionnaire, then every `--check`. Claims and glossary builders insert
   their blocks by heading id, or the Markdown keeps marker comments as
   placeholders. Exit: one command reproduces the published page; all
   existing tests pass.
6. **Cut-over.** Update `tools/README.md`, `README.md` and `AGENTS.md`; add
   `build-book.py --check` to fail when the committed HTML is stale; repoint
   or retire the annotation editor. Exit: one tagged release and a changelog
   entry.
7. **Optional, later.** Move inline CSS to `assets/textbook.css`; EPUB/PDF
   output. Both change the output, so only after cut-over.

## Risks

- Silent text drift (quotes, whitespace, entities, ordering) breaking claim
  excerpt validation. Phase 1 is the defence.
- Pandoc's default structure (footnote section, table markup, section
  wrapping) differs from the book's; each needs a filter or template.
- Two sources of truth during transition. Freeze HTML prose edits from phase 4
  to cut-over, or every fix is made twice.
- Too much raw HTML. If more than about a quarter of the source is raw HTML,
  most of the benefit is lost. Phase 3 is the honest test.

## Phase 0 decision (2026-11-26)

- **Goals:** all four. Easier editing, cleaner diffs and review, and safer
  AI-assisted editing, plus EPUB/PDF output from the same source.
- **Consequence:** the built HTML must stay equivalent to the baseline through
  phases 1 to 6. EPUB/PDF stays in phase 7. Because other formats are a goal,
  the phase 2 mapping should prefer semantic fenced divs over raw HTML wherever
  a construct has meaning beyond styling, so that the same source can drive an
  EPUB/PDF writer later.
- **Annotation editor:** decision deferred to phase 6. Until then it keeps
  working on the HTML as now.

## Phase 1 status (2026-11-26)

- `tools/html_equivalence.py` compares two HTML files through a canonical,
  normalised serialisation. It ignores only rendering-irrelevant differences
  (attribute and class-token order, character references, void-element syntax,
  ASCII whitespace collapse and whitespace at block boundaries). It keeps
  NBSP, inline spacing, comments and `script`/`style`/`pre` content
  significant. It rejects malformed input rather than repairing it.
- Baseline recorded in `data/markdown-baseline.json` (commit `a740bd2`, whose
  book is unchanged from `0e3d4f8`). The canonical snapshot is written to the
  ignored `outputs/markdown-conversion/`.
- `tools/test-html-equivalence.py` (11 tests) covers: the book equals itself;
  the book rewritten by a different serialiser (newlines around blocks,
  reversed attributes, self-closing voids, numeric references for all
  non-ASCII) is equivalent; one-word, anchor, class, marker and inline-markup
  edits fail; `--section` scoping; the manifest matching its commit; rule
  cases; and malformed input.
- Exit criterion met: self-comparison passes; deliberate edits fail.
- The baseline must be re-recorded at the phase 4 freeze, because prose edits
  will continue until then. Re-record only on purpose:
  `python tools/html_equivalence.py --record-baseline`.

## Phase 2 status (2026-11-26)

- Mapping in `data/markdown-mapping.json` (30 constructs covering all 191
  classes and 71 element types) and explained in
  [`markdown-mapping-spec.md`](markdown-mapping-spec.md).
- `tools/markdown_mapping.py` checks the mapping is complete and not stale,
  and measures the raw-HTML share: 3.7% of authored words, 14.1% of authored
  elements, both under the 25% stop threshold.
  `tools/test-markdown-mapping.py` (7 tests) guards completeness, staleness,
  duplicates and the threshold.
- Exit criterion met: every surveyed class has a mapping or is marked raw.
- New in the conversion: stage maps and chapter navigation become derived from
  front matter and file order (currently hand-maintained), and footnote
  numbering moves into the build. The spec lists nine points phase 3 must
  verify before relying on these.

## Phase 3 status (2026-11-26)

- **Pilot passed for Chapters 2 and 3.** Chapter 3 was added because Chapter 2
  has no footnotes or maths.
  - Each chapter was converted with `tools/markdown/html_to_md.py`, rebuilt
    with Pandoc and `tools/markdown/book.lua`, and spliced into a copy of the
    repository.
  - After every generator ran, the book and all 12 root HTML pages were
    equivalent to the live files.
  - All 19 generator, check and test runs behaved exactly as on an unchanged
    copy: `python tools/markdown/pilot.py book/02-boolean-admission.md
    book/03-bm25-ranking.md`.
- **Readability.** One sentence per line, native lists, pipe tables,
  footnotes and `$…$` maths. There are no inline raw-HTML blocks. The four
  worked diagrams are kept in `book/figures/` (45 lines, against 702 lines of
  chapter Markdown).
- **Exit criterion met.**
- **Faults found in the existing repository:**
  - `maintain.py` could not run on the live book after `37dc2e3` added
    `tabindex` to the article tag. Fixed in its own commit; on the current
    book it then makes no changes.
  - `maintain.py` also reported "From language model to retrieval encoder:
    0 table(s) but 1 'Table n.n' label(s)". This was a false positive: Table
    6.1 gained `class="token-comparison"` in `49256c0`, and `maintain.py`
    matched only a bare `<table>`. Fixed in `536afac` on `main`, brought here
    as `6125013`. `maintain.py` now reports no problems, and the pilot passes
    with it exiting 0 in both copies.
- **Phase 4 readiness.** The converter runs on all 23 chapter and appendix
  sections without errors and leaves 54 blocks as raw HTML with warnings:
  - 9 query-flow figures;
  - 11 tables with attributes;
  - 9 table labels not directly followed by a table;
  - horizontal rules, `div.orientation`, evidence stacks, three definition
    lists and two maths wrappers;
  - appendix section ids (`app-A`, not `sec-KEY`).

  Navigation needs overrides for exercises, appendices and the back-matter
  link. Back sections, part dividers and the front matter have not been
  attempted.
- **`book/` status.** `book/02-boolean-admission.md` and
  `book/03-bm25-ranking.md` are pilot outputs. Until the phase 4 freeze, the
  HTML stays the source and these files are regenerated, not edited.

## Phase 4 status (2026-11-26)

- **Whole book converted.** `book/` holds 40 ordered source files (39
  Markdown, plus an empty claims-register marker), `template.html` and 33
  diagram files. These replace the phase 3 pilot files. They are produced by
  `python tools/markdown/html_to_md.py --book book`.
- **Exit criterion met.** `python tools/markdown/pilot.py --book book` builds
  the whole page from those sources alone, with nothing kept from the live
  article, and runs the generators until they settle (three rounds).
  - The book, and every root HTML page after the companion builders, are
    equivalent to the live files.
  - The build matches the phase 1 baseline (`a740bd2`). The live book is
    unchanged since.
  - All 19 generator, check and test runs match the control copy.
- **Derived rather than hand-written:**
  - all 27 navigation bars, using the rules in the mapping;
  - all 15 stage maps but one;
  - both tables of contents and the asset indexes (`maintain.py`);
  - the footnotes list, the glossary wrappers and lookup, and the claims
    register and links (existing generators).
- **Raw HTML:** 0.7% of source characters inline, in five blocks listed in
  the spec, plus 9.6% in the diagram files. This is down from 54 inline blocks
  at the start of the phase, and well under the 25% threshold.
- **Faults found and fixed during the phase:** Pandoc's div-to-section
  conversion, line breaks and joined raw blocks adding spaces, display maths
  reformatting, table labels separated from their tables by generated links,
  and lost list start numbers. Each now has a unit test (25 in
  `tools/test-markdown-build.py`).
- **Freeze, revised.** The plan froze HTML edits from phase 4 to cut-over.
  That is not needed yet, because conversion is repeatable:
  - keep editing `search-textbook.html` and rerun the conversion;
  - `python tools/markdown/html_to_md.py --check book` and the unit tests
    report when `book/` has fallen behind;
  - freeze only for the cut-over commit itself, then re-record the baseline.
- **Not done:**
  - the build still runs in a scratch copy (making it the in-place build is
    phase 5);
  - EPUB/PDF (phase 7);
  - the annotation-editor decision (phase 6).

## Phase 5 status (2026-11-26)

- **`python tools/build-book.py` is the single build command.** It builds
  `book/`, runs the generators until they settle, and rebuilds the digest and
  vendor questionnaire. It has three modes:
  - `--check` builds in a scratch copy and compares every root page; it takes
    about 8 seconds;
  - `--out DIR` builds into a copy of the repository;
  - with no option it builds in place.
- **The in-place build is refused** while `book/book.json` says
  `"source_of_truth": "html"`, so it cannot overwrite hand edits that `book/`
  lacks.
- **Exit criterion met.** One command reproduces the published page:
  - `--check` passes;
  - 10 of 12 pages are byte-identical, and `search-textbook.html` and
    `read-this-first.html` are equivalent (reformatted).
- **Deterministic and idempotent.** Two builds are byte-identical on all 12
  pages. Rehearsed in a scratch copy with the source set to `"markdown"`:
  - the strict byte-level `--check` passes;
  - an in-place rebuild changes nothing;
  - an unbuilt Markdown edit makes `--check` fail.
- **Existing tests:**
  - **Python suites:** all pass in the pilot (digest, glossary, claims,
    questionnaire, equivalence, mapping, build). The four new
    `tools/test-build-book.py` tests pass.
  - **The 11 Node checks** (six browser checks, three lab tests, two
    annotation suites) give identical passing results on the live repository
    and on the built copy. They were run with Chromium in place of Edge,
    because these scripts hard-code `channel: 'msedge'` and Edge is not
    installed here. The repository's scripts were not changed.
  - **Fault found in the existing repository:** `tools/test-evaluation-kit.py`
    fails on the live repository as well as the built one. It expects three
    links to `evaluation-kit.html` in the book, and commit `37dc2e3` added a
    fourth. Not changed here.
- **Not done:** the cut-over itself (phase 6): set the source of truth to
  `"markdown"`, commit a fresh in-place build, update `README.md`,
  `tools/README.md` and `AGENTS.md`, decide on the annotation editor, and
  re-record the baseline.
